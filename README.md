
## Как запустить

Нужен .NET 8 SDK (`dotnet --version` должен показать 8.x).

```bash
dotnet run --project VyshKat.App   # запустить приложение
dotnet test                        # прогнать тесты
```

Оба проекта лежат в `VyshKat.sln`.

## Как работает приложение

Это интерактивная консольная программа: никаких данных для демонстрации в коде не зашито, весь парк пользователь вводит сам. 
При запуске показывается меню:
  1 - добавить транспорт (с техосмотром)
  2 - добавить вещь на баланс
  3 - отчёт по количеству
  4 - суммарное энергопотребление
  5 - техника для новичков
  6 - вся инвентарная ведомость
  0 - выход

При добавлении транспорта приложение спрашивает тип (самокат / электровелик / велосипед), номер, название, оценку простоты и, если техника электрическая, суточный расход энергии. После ввода оно сразу прогоняет технику через техосмотр и пишет, принята она или отклонена. Вещи (шлем, зарядная станция) добавляются пунктом 2.

Меню рассчитано на ввод с клавиатуры.

Приложение корректно понимает точку и запятую в десятичных числах и завершается, когда ввод заканчивается.

## Что где лежит

```
VyshKat.App/
  Domain/     интерфейсы (IInventoryItem, IEnergyConsumer,ITransport) и сущности
  Services/   ITechInspect / TechInspectService (техосмотр) и ParkManager (учёт)
  Program.cs  сборка DI-контейнера, меню и обработка ввода
VyshKat.Tests/ юнит-тесты (xUnit + Moq)
```

Сущности: `Scooter`, `EBike`, `Bicycle`, `Helmet`, `ChargeStation`.

## Почему модель такая

Есть три независимых признака:

* стоит на балансе — есть инвентарный номер (`IInventoryItem`);
* тратит энергию — есть суточный расход (`IEnergyConsumer`);
* это транспорт — едет и проходит техосмотр (`ITransport`).

Если смотреть на вещи в парке, видно, что комбинации бывают разные. Поэтому это три отдельных интерфейса, а не один общий класс с кучей `if`. Так каждый класс реализует ровно то, что про него правда.

### 1. Какой принцип SOLID применён явнее всего и где

ISP (Interface Segregation Principle) — в `Domain/Interfaces.cs`. Интерфейсы разрезаны по смыслу, как раз чтобы никого не заставлять реализовывать лишнее.
Хороший пример — `Bicycle`: он транспорт, но не `IEnergyConsumer`. Если бы был один интерфейс, велосипеду пришлось бы отдавать фиктивный расход энергии. То же с `Helmet` — шлем не проходит техосмотр и не обязан быть транспортом.

DIP: `ParkManager` держит поле `ITechInspect` и зависит от интерфейса, а не от `TechInspectService`. 

### 2. Какой принцип сознательно ограничен и почему это нормально

Ограничен SRP у `ParkManager`. Сейчас он делает три вещи: хранит список (`_things`), считает энергию и фильтрует технику для новичков.

Для трёх самокатов появляется лишний слой абстракции, который ничего не даёт. Если парк вырастет и понадобится реальное хранилище, `ParkManager`
можно будет разбить на репозиторий и сервис — сейчас это преждевременно.

### 3. Что будет, если добавить что-то новое

* Новый вид транспорта — ничего не ломается. Достаточно объявить класс и реализовать `ITransport` и, если он ест ток, `IEnergyConsumer`.
  `ParkManager` его подхватит сам, править его не придётся.
* Склад запчастей — тоже ничего. Запчасть наследует `IInventoryItem` и ложится на баланс через `AddThing`, как шлем.

### 4. Какие тесты фиксируют решения и как подменяется зависимость

Техосмотр — `ParkManagerTests`:

* `AddTransport_WhenInspectOk_ReturnsTrue` — техосмотр пропустил, техника принята;
* `AddTransport_WhenInspectFails_ReturnsFalse` — отказ, техника не попала в парк.

Плюс отдельные тесты самого сервиса в `TechInspectServiceTests`
(`[Theory]` проверяет границы оценки 1..10 и отказ на 0 и 11).

Для новичков — `GetForNoobs_FiltersCorrectly`: кладу два самоката с
оценкой 4 и 7, проверяю, что вернулся только тот, у которого 7.

Отчёт по количеству — `CountTransports_And_CountThings_AreCorrect`.

Подмена зависимости сделана через Moq:

```csharp
var mockInspect = new Mock<ITechInspect>();
mockInspect.Setup(m => m.CheckTransport(It.IsAny<ITransport>())).Returns(false);
var manager = new ParkManager(mockInspect.Object);
```

То есть техосмотр не запускается по-настоящему: мы говорим "считай, что он вернул false" и проверяем, что менеджер правильно на это реагирует. Работает это только потому, что `ParkManager` принимает `ITechInspect` через конструктор.

### 5. Что делал ИИ

Применялся как вспомогательный инструмент при работе над проектом: для обсуждения структуры и подходов, проработки отдельных частей реализации, подготовки тестов и проверки граничных случаев. Все предложенные решения сверялись с требованиями задания и проверялись практическим запуском.
